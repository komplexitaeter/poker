Fish tokens – technical concept

Backend concept (Ben) for discussion with Andreas. Static page, nothing is implemented. Clickable UI: fish-tokens mockup (Delia). Back to all mockups.

Summary: supporters buy a supporter pack through Paddle and get tokens on an anonymous voucher code (no account, no e-mail on our side). Tokens are loaded onto emojis or a fish blocker. Every throw is decided in MySQL by a new api/react.php (free daily quota first, then loaded tokens, blocker at the target); poker-msg only fans the result out to the team, like pull since B-81.

2 Data model (MySQL 8.0, new tables utf8mb4)

-- one wallet per voucher code; the code itself is never stored
create table pok_wallets_tbl (
  id            int not null auto_increment primary key,
  ref           char(12) not null,            -- public, random; goes to Paddle custom_data, receipts, support
  code_hash     char(64) not null,            -- sha256(normalized code), hex
  balance       int not null default 0,       -- tokens not yet loaded
  creation_date timestamp not null default current_timestamp,
  last_used     timestamp not null default current_timestamp,
  unique key u_ref (ref), unique key u_code (code_hash),
  check (balance >= 0)
) default charset=utf8mb4;

-- loaded tokens per emoji; 'blocker' is a pseudo emoji = fish blocker charges (mock calls it 'shield'; name to agree with Fred)
create table pok_wallet_loads_tbl (
  wallet_id  int not null,
  emoji_code varchar(12) not null,            -- cake, heart, …, fish, blocker
  tokens     int not null default 0,
  primary key (wallet_id, emoji_code),
  check (tokens >= 0)
) default charset=utf8mb4;

-- active blocker: row exists = user is protected (charges come from the wallet's 'blocker' load)
create table pok_blockers_tbl (
  user_id       varchar(16) not null primary key,   -- pok_players_tbl.id
  wallet_id     int not null,
  creation_date timestamp not null default current_timestamp,
  key i_wallet (wallet_id)
) default charset=utf8mb4;

-- B-139 free quota, replaces the in-memory counter in poker-msg (survives restarts)
create table pok_react_quota_tbl (
  user_id    varchar(16) not null,
  emoji_code varchar(12) not null,
  day        date not null,                   -- utc_date(), same boundary as the board
  primary key (user_id, emoji_code, day)
) default charset=utf8mb4;                    -- event job deletes day < utc_date() - 2

-- rate limit, one row per thrower; event job deletes rows older than 1 day
create table pok_react_users_tbl (
  user_id    varchar(16) not null primary key,
  last_throw timestamp(3) not null
) default charset=utf8mb4;

-- purchases; Paddle transaction id UNIQUE = idempotent credit
create table pok_purchases_tbl (
  id             int not null auto_increment primary key,
  paddle_txn_id  varchar(64) not null,
  wallet_id      int not null,
  price_id       varchar(64) not null,
  tokens         int not null,
  tokens_revoked int not null default 0,      -- refunds/chargebacks
  amount_minor   int not null, currency char(3) not null,
  creation_date  timestamp not null default current_timestamp,
  unique key u_txn (paddle_txn_id), key i_wallet (wallet_id)
) default charset=utf8mb4;

-- every processed webhook event once (Paddle retries and may send twice)
create table pok_paddle_events_tbl (
  event_id     varchar(64) not null primary key,
  event_type   varchar(64) not null,
  processed    timestamp not null default current_timestamp
) default charset=utf8mb4;

Store the code or only a hash?

The code is a bearer secret like the team id (whoever knows it may spend). Unlike the team id it carries money value, and grafana_usr reads the same MySQL from outside.

Recommendation: store only sha256(code). Lookup by hash is a plain unique-key lookup, costs nothing, and a DB dump or a too-wide Grafana grant does not leak spendable codes. No salt needed: the code has 80 random bits, so precomputation is useless. Consequence: a lost code cannot be "shown again" – support can find the wallet via the Paddle receipt (transaction id → ref) and rotate it to a new code (admin action in stats.php), but only after checking the buyer's e-mail in the Paddle dashboard against the sender of the request – the transaction id alone is printed on the receipt and proves nothing. Additionally: no grants for grafana_usr on the wallet tables.

Code format: 16 characters Crockford Base32 (no I, L, O, U) = 80 bits, shown as FISH-7K2Q-9MXD-H4TR-B8WN. Normalized before hashing (upper case, dashes and spaces removed, O→0, I/L→1). Generated with random_bytes(). Alphabet, length and normalization must be identical in the generator (PHP) and in the board's input check (Fred) – the mock's FISH-7KQ2-M9XA is only a shortened placeholder.

Renew: update pok_wallets_tbl set code_hash = :new where code_hash = :old – one statement, old code invalid immediately, ref, balance and loads stay. This is the emergency brake: every other browser with the old code gets 401 and shows "code no longer valid"; whoever renewed shares the new code again with the people who should keep spending. Renew also deletes the wallet's rows in pok_blockers_tbl (whoever keeps the new code re-activates the blocker).

Risk (accepted with Andreas' decision): because the code is shared, everyone who knows it can also renew it – and thereby lock out the buyer and everyone else and take the remaining tokens. There is no owner to protect. Mitigation is only the support rotation above (buyer e-mail checked in Paddle). Optional later: "gift as transfer" – move a chosen amount to a fresh code, so the giver's own code never leaves their hands.

Sharing and redeem (decided by Andreas, 2026-11-19)

The balance belongs to the code, the code is simply shared. Everyone who knows it spends from the same balance and loads – using it on a second device and giving it as a gift are the same thing. Redeem = check the code and store it in this browser; no transfer, the code stays valid for everyone who has it. Simultaneous spending from several browsers is safe because every spend is one guarded update (section 4).

Gift links: no code in the query string in production (?redeem= is a mock deep link only) – it would end up in access logs, browser history and referrers. If a link is wanted at all, use a fragment #redeem=… (never sent to the server) and remove it right away with history.replaceState; otherwise copy the code only.

Charset note: pok_players_tbl.id is utf8mb3. We never join across the charsets; react.php reads the target's user id by mkey and passes it as a parameter, so indexes are used.

3 Endpoints

Conventions as today: require_post(), require_team(), ids via get_id_param(), prepared statements only, JSON via json_encode. All wallet endpoints are called from the board, so they also require a valid team id (cheap barrier against random calls). New: the voucher code travels in the header X-Wallet-Code, never in the URL – the query string ends up in nginx access logs, and a custom header forces a CORS preflight, so other sites cannot send it. Prerequisite: the API never sends any Access-Control-Allow-* header (otherwise the preflight protection is gone).

Ids in the POST body: t, id, to and the other parameters of the new endpoints travel as form fields in the POST body, not in the query, so user ids and team ids do not land in access logs either. This needs a body variant of get_id_param() (same rules, INPUT_POST); existing endpoints stay as they are.

Uniform answers: every endpoint that takes X-Wallet-Code (react, wallet/redeem, load, blocker, renew, checkout_start with code) answers an unknown or malformed code with the same 401, and all of them sit behind the same nginx limit_req zone. 409 only means "known code, not enough tokens".

Moves in wallet_load are one transaction with guarded updates, e.g. update pok_wallets_tbl set balance = balance - ? where id = ? and balance >= ? → 0 rows = 409; then insert … on duplicate key update tokens = tokens + ?. Two browsers loading from the same code at once cannot overdraw the balance.

paddle_webhook.php

  1. POST only (405 otherwise); body size limited (e.g. 64 KB, nginx client_max_body_size on this location and a length check in PHP). Raw body via file_get_contents('php://input'), verify before json_decode.
  2. Header Paddle-Signature: ts=…;h1=…: hash_hmac('sha256', ts . ':' . raw, secret), compare with hash_equals (accept any h1, Paddle sends two during secret rotation). Reject if |now − ts| > 300 s (replay window). Secret in config.php (_PADDLE_WEBHOOK_SECRET), never in the repo. Sandbox and live are separate: own secret, own price ids, own API key; staging uses only the sandbox set, live only the live set.
  3. Transaction: insert into pok_paddle_events_tbl (event_id …) – duplicate key → already processed → 200.
  4. transaction.completed: wallet by custom_data.wallet_ref; tokens only from our price table (PACKS[price_id] in code/config), never from client data. The checkout fixes the quantity to 1; the webhook still sums all items (PACKS[price_id] × quantity) and credits only if every price id is known, the paid total is > 0 (100 % discount codes!) and currency/amount match the pack. Anything else: log, no credit. Insert purchase (txn UNIQUE), add balance.
  5. adjustment.created/updated with action refund or chargeback and status approved: find the purchase via the adjustment's transaction_id, revoke (section 5). Over several partial refunds the sum of revoked tokens never exceeds the purchase's tokens (tokens_revoked + n <= tokens).
  6. Commit, 200. Unknown wallet_ref or price → log, 200 (otherwise Paddle retries forever), handle manually.
  7. Logging: never log the raw body (it contains names, e-mails, addresses). Log lines carry only event_id, txn_id, price_id and ref.

Wallet before or after checkout?

Recommendation: create the wallet before the checkout (checkout_start.php) and give Paddle only the public ref. The browser already holds its code when the payment finishes, so there is no second secret to hand over after the webhook, and a late webhook just means "pending" until the balance changes. The code itself never reaches Paddle (dashboard, exports, receipts). The alternative – issue the code in the webhook – needs a way to fetch it by transaction id, which turns the transaction id (printed on the receipt) into a second bearer secret. Wallets created but never paid are deleted by the event job after 30 days.

4 Throw and blocker logic (react.php)

begin;
  -- who: the thrower is identified by its user id (secret, like today in the board), never by a client mkey
  select mkey from pok_players_tbl where id = :id and team_id = :t;              -- none → 403
  select id, mkey from pok_players_tbl where mkey = :to and team_id = :t;        -- none / self → 404
  -- rate limit ≈3/s: affected rows 0 → 429 (nothing spent)
  insert into pok_react_users_tbl values (:id, now(3)) on duplicate key update
    last_throw = if(last_throw < now(3) - interval 300000 microsecond, now(3), last_throw);
  -- nudge: no quota, no tokens (only rate limit)
  insert ignore into pok_react_quota_tbl values (:id, :emoji, utc_date());        -- 1 row → source = free
  update pok_wallet_loads_tbl l join pok_wallets_tbl w on w.id = l.wallet_id
     set l.tokens = l.tokens - 1
   where w.code_hash = :hash
     and l.emoji_code = :emoji and l.tokens > 0;                                  -- else: 1 row → token, 0 → rollback, 409
  -- blocker: only for fish (open question). Paid throw → consumes one charge of the TARGET's wallet:
  update pok_wallet_loads_tbl l join pok_blockers_tbl b on b.wallet_id = l.wallet_id
     set l.tokens = l.tokens - 1
   where b.user_id = :target_user_id and l.emoji_code = 'blocker' and l.tokens > 0;  -- 1 row → blocked
  -- free throw → bounces for free, no charge consumed (only checks that charges are left):
  select 1 from pok_blockers_tbl b join pok_wallet_loads_tbl l on l.wallet_id = b.wallet_id
   where b.user_id = :target_user_id and l.emoji_code = 'blocker' and l.tokens > 0;  -- row → blocked
commit;
notify_react($t, $from_mkey, $to_mkey, $emoji, $blocked);                        -- after commit, never on 4xx
  • Atomic: two clicks or two devices on the same wallet cannot overspend; the last token goes to exactly one request, the other gets 409. Two paying throwers at a blocker with two charges: each consumes one, the third passes.
  • Blocked throws are paid by the thrower: the thrower's free quota or token is spent. The target's charge is spent only by token-paid throws. Reason (Sina): user ids are generated by the browser, so anyone can get unlimited free throws with new ids; if free throws consumed charges, a script could drain a paid blocker for free.
  • The free quota per user id is not robust (new id = new quota, as today with B-139 in localStorage). We accept that: free throws cost no money, and with the rule above they cannot destroy anything paid.
  • Rate-limit assumption: the upsert relies on mysqli's default without CLIENT_FOUND_ROWS (an unchanged row reports 0 affected rows). db_init() must not set that flag; a test covers it.
  • No auto-retry for react.php (B-135 write-retry excluded): a retry after a timeout could spend twice. A lost throw is cheaper than a double one.
  • Quota per user id (as the board already counts it in localStorage, B-139), UTC day. poker-msg drops its in-memory quota.

Messages

 API → poker-msg (UDP 127.0.0.1:8444):  react:<team_id>:<from_mkey>:<to_mkey>:<emoji>:<0|1>
 poker-msg → team (WebSocket):          react:<from>:<to>:<code>            (not blocked, unchanged format)
                                        react:<from>:<to>:<code>:blocked    (fish flies to target, bounces back to from)

The blocked flag is a fixed last field on UDP (not optional) because team ids may contain : – poker-msg splits the last four fields from the right, the rest is the team id. Old boards ignore the :blocked variant (their regex is anchored), so the rollout is safe. The echo contains everything a board needs to animate; nobody has to reload dao.php.

5 Abuse and security

  • Guessing codes: 80 bits; even 1,000 tries/s for years finds nothing. Still: one nginx limit_req zone for all endpoints that take X-Wallet-Code (react, wallet/redeem, load, blocker, renew, checkout_start), e.g. 10/s per IP with burst – react needs headroom for a team behind one NAT. Mostly protects the DB. Unknown code: the same 401 everywhere, no timing difference that matters (hash lookup).
  • Refunds and chargebacks: Paddle adjustment events (refund, chargeback; only when approved). Revoke tokens proportional to the refunded amount (rounded up), taken from balance first, then from loads, then blocker charges; never below 0 (CHECK constraints). Tokens already thrown are gone – we accept that loss (amounts are small). Record in tokens_revoked; repeated chargebacks from one wallet → close it manually.
  • Personal data: Paddle is merchant of record and holds e-mail, address, payment data. We store only transaction id, price id, amount, tokens, wallet id – not customer_id, not e-mail. The code never goes to Paddle. Privacy policy needs a Paddle paragraph, including the linkability: Paddle customer → transaction → ref → wallet → user id (blocker, throws) → teams. Not stored together, but joinable by us.
  • Logs: X-Wallet-Code never appears in logs or error messages (no nginx log_format with it, no PHP error output of headers); webhook logs see above.
  • Retention: event job deletes quota rows older than 2 days, pok_react_users_tbl rows older than 1 day, unpaid empty wallets after 30 days, and blocker rows whose wallet has no charges left; renew deletes the wallet's blocker rows.
  • Team id rules unchanged: every endpoint except the webhook checks require_team(); react.php additionally checks that thrower and target are players of that team, so a code alone cannot throw into foreign teams.
  • CSRF-like calls: there is no session or cookie to abuse – every request needs secrets the attacker would have to know (team id, user id, code). The custom header X-Wallet-Code additionally prevents simple cross-site form posts (preflight, no CORS allowed). The webhook is authenticated only by its HMAC.
  • Spoofing reactions: poker-msg no longer accepts react from WebSocket clients; UDP listens on 127.0.0.1 only. The thrower's mkey comes from the DB, not from the client (today a client could claim any from).
  • Code in the browser: localStorage, like the user id. Shown in the wallet panel for copying/gifting; "Renew code" is the answer to "I shared it by mistake". New risk: an XSS on the board could now read a code with money value from localStorage. Prerequisite before step 7: a Content-Security-Policy for board.html – as its own future backlog item.
